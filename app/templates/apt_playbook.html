Delivery — prebuilt vs realtime

Default Two ways an image reaches the page. Prebuilt: baked offline before deploy — 0 ms on the visit, $0 per visit, hard-capped at {{ caps.states_per_target }} states per image target, {{ caps.images_per_tenant }} baked images per website, {{ caps.images_global }} global. Realtime: the page paints instantly with a brand gradient, then swaps in the generated image in ~2s; each generation costs about ${{ '%.3f'|format(caps.per_gen_usd) }} and is cached by key so it is paid once. A ${{ '%.0f'|format(caps.ceiling_usd) }}/day per-website spend ceiling backstops the realtime lane — past it, the neutral prebuilt/gradient ships instead. Every API call is cost-logged to the spend ledger, including failures.

How copy is made

Default methodology signal stack → route → objections → say/allude/hold → pre-authored reframes
1

Default — deterministic slot-fill, provable by construction

Default Copy starts from the same shared signal stack as images, routes the visitor to an audience (hire / upskill / individual / neutral), ranks their likely objections, and then fills each named slot on the page from a pre-authored catalog. No AI writes at visit time, so the words are provable by construction and cost $0 — the same inputs always produce the same page, and every changed slot carries a receipt.

Every fact obeys a three-level surface policy per slot: say — first-party, declared facts may be quoted out loud; allude — inferred context (like an IP-derived industry) may steer the framing but is never quoted; hold — the fact never reaches the page at all. Objections are answered with pre-authored reframes written at the allude level.

Customize The sd-policy control per text slot in the designer, backed by the policy field per text target in {{ files.sections }}.
2

The five persuasion strategies

Default A strategy changes the frame — which provable claims lead, under what headline and call-to-action — and never the facts. Any claim the truth Gate blocks is dropped from every strategy alike.

3

Opt-in — the generative lane

Default Off unless you switch a slot's mode to generative. When you do: your prompt proposes candidate lines → every candidate runs through the real truth Gate (claims, hygiene, the per-line copy checks) → only cleared copy ever enters the servable pool → the pool is cached so an identical visit replays byte-identically. A candidate that recites a competitor, invents a number, or touches a held fact is structurally unservable — not filtered, excluded by construction. Prebuilt bakes the pool offline before deploy; realtime builds it on first visit and caches by key.

Customize sd-mode (deterministic ↔ generative), the sd-prompt box, and sd-workflow (prebuilt / realtime) per text slot in the designer — all staged to {{ files.sections }} in the drawer; nothing saves live.
4

Always on — long-running A/B + drift pause

Default Every decision (each slot, each image target) runs a long-lived A/B over its cleared pool, per audience route, with a random-control holdout so lift is measured, not asserted. If a source changes or a legal hold lands, drift monitoring re-verifies only the affected claims and pauses only the dependent variants — the rest of the page keeps optimizing.

Customize Runs automatically per decision — no switch to flip. The posteriors, lift, and any paused arms are readable on each section card in the designer.

Personalization for AEO — Agent Engine Optimization

Roadmap · point of view a thesis about the next visitor — nothing in this chapter is built

Roadmap · point of view. Everything below is an approach we intend to take, framed as such — no sentence here describes a shipped capability.

1

The thesis — the next visitor isn't always human

Buying agents, research agents, and answer engines increasingly read pages, compare claims, and act on what they find. The approach: treat the agent as an audience, not an adversary. apt's architecture would suit this unusually well — here is the point of view, point by point.

  • Detect the agent segment the same way network type is detected today — on this roadmap, the agent simply becomes another audience_route, flowing through the exact routing the human segments use.
  • The receipt would be the AEO asset. Agents rank what they can verify — a page where every claim carries a machine-readable source and Gate verdict is, in this view, exactly what answer engines could trust and cite.
  • The truth Gate as ranking advantage. An apt page structurally cannot ship a claim the Gate blocks — so, as an approach, provability itself becomes the optimization target an agent would reward.
  • Personalizing for agents would mean: structured claims, per-claim citations, deterministic replies (same input → same page — the property agents prize), and machine-legible provenance strips.
  • The same per-decision A/B machinery could optimize per agent engine — segment = which engine is reading — inside the same truth boundary that governs every human variant.

The close, and the tagline it earns: when the visitor is an AI, proof isn't a nicety — it's the ranking function.

Where this would live No customize chip — this chapter is roadmap. The agent segment would slot into the registry's channel/route vocabulary in {{ files.sections }}; the per-claim receipts it depends on already ship on every page today.
